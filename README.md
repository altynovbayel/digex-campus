# DIGEX Campus

Образовательная платформа по практическому использованию ИИ (Claude и ChatGPT):
кабинет ученика и панель администратора. React + TypeScript + Vite, авторизация — Supabase.

## Запуск

```bash
npm install
npm run dev        # dev-сервер Vite (порт 5173, если свободен)
npm run typecheck  # проверка TypeScript
npm run lint       # ESLint
npm run build      # production-сборка в dist/
```

Без настроенного Supabase кабинет закрыт и показывает инструкцию — демо-данные не подставляются.

## Режимы

| Режим | Как включить | Что происходит |
|---|---|---|
| Обычный | `.env.local` с данными Supabase | Регистрация, вход, профиль из базы. Кабинет и админка защищены. |
| Демо (только разработка) | `VITE_DEMO_MODE=true npm run dev` | Вымышленный ученик и переключатель состояний доступа. Вход не выполняется. В production-сборке демо всегда выключено. |

## Настройка Supabase

Используйте **отдельный новый проект** Supabase только для DIGEX Campus.

1. **Создайте проект** на supabase.com (New project). Запомните пароль базы — в приложение он не нужен.
2. **Переменные окружения.** Скопируйте шаблон и заполните его:
   ```bash
   cp .env.example .env.local
   ```
   - `VITE_SUPABASE_URL` — Project Settings → Data API → Project URL.
   - `VITE_SUPABASE_PUBLISHABLE_KEY` — Project Settings → API Keys → **Publishable key** (`sb_publishable_…`).

   **Secret key / service_role в `.env.local` и в код не добавлять.** Всё с префиксом `VITE_` попадает в браузерный
   JavaScript, поэтому `vite.config.ts` останавливает `npm run dev` и `npm run build`, если в любой `VITE_`-переменной
   найден секретный ключ, а в `VITE_SUPABASE_PUBLISHABLE_KEY` — не publishable/anon-ключ. `.env.local` исключён из Git.
3. **Примените SQL строго по порядку** (каждый файл — отдельный запрос в SQL Editor):
   1. `supabase/migrations/20261117000000_profiles.sql` — профили и роли (этап 2);
   2. `supabase/migrations/20261118000000_learning.sql` — разделы, уроки (этап 3А);
   3. `supabase/seed/initial_content.sql` — начальное наполнение: Claude и ChatGPT по 6 уроков.
      Повторный запуск безопасен: дублей нет, правки администратора не перезаписываются;
   4. `supabase/manual/check_legacy_access.sql` — **только чтение**: проверка старых оплат по разделам;
   5. `supabase/migrations/20261119000000_course_access.sql` — единый доступ к курсу.
      Если в старой таблице `payments` есть записи, миграция остановится целиком и ничего не изменит:
      правило переноса старых оплат выбирается отдельно (см. результат шага 4).
   6. `supabase/migrations/20261120000000_quizzes.sql` — тесты, попытки и результаты (этап 3Б);
   7. `supabase/seed/quizzes.sql` — начальные тесты: по 3 вопроса к каждому из 12 уроков.
      Повторный запуск безопасен: тест создаётся, только если у урока его ещё нет; попытки не создаются.
   8. `supabase/migrations/20261121000000_quiz_write_locks.sql` — исправление: изменение вопросов только через функции
      с единым порядком блокировок (тест → вопросы), прямая запись в таблицу вопросов клиентам запрещена.
   9. `supabase/migrations/20261122000000_quiz_followups.sql` — создание теста только функцией `admin_create_quiz`
      (прямой INSERT в `quizzes` клиентам запрещён), согласованная проверка урока и раздела при отправке попытки,
      нормализация разреженных позиций вопросов при добавлении.
  10. `supabase/migrations/20261123000000_quiz_concurrency.sql` — перестановка уроков с блокировкой `FOR NO KEY UPDATE`
      и проверка теста, урока и раздела при отправке из свежего снимка после блокировки теста.
  11. `supabase/migrations/20261124000000_quiz_move_version.sql` — перестановка вопроса с проверкой версии теста
      (устаревший порядок в редакторе не приводит к лишнему сдвигу).
  12. `supabase/migrations/20261125000000_admin_get_quiz.sql` — загрузка теста в редактор одним запросом
      (версия и порядок вопросов из одного снимка).
  13. `supabase/migrations/20261126000000_attempt_answers_privacy.sql` — закрывает ученикам колонку `answers`
      (ключи ответов) в истории попыток. Зависит только от шага 6 (`20261120000000_quizzes.sql`).
      **Рекомендуемый порядок для новой базы:** выполнить сразу после шага 6, до наполнения (шаг 7) и первых попыток.

   Фактическое состояние настоящей базы, порядок, в котором она применялась, и результаты ручной проверки —
   в [`docs/stage-status.md`](docs/stage-status.md).

   Способы:
   - **SQL Editor** (проще): Dashboard → SQL Editor → New query → вставьте содержимое файла → Run.
   - **Supabase CLI**:
     ```bash
     npx supabase login
     npx supabase init            # если CLI попросит config.toml; миграции не затрагиваются
     npx supabase link --project-ref <ref-вашего-проекта>
     npx supabase db push
     ```
     `db push` применяет только миграции. **Начальное наполнение он не выполняет:** после него обязательно выполните
     в SQL Editor (Dashboard → SQL Editor → New query → вставить → Run) по порядку
     `supabase/seed/initial_content.sql`, затем `supabase/seed/quizzes.sql`.
     Не смешивайте способы: если часть миграций уже применена через SQL Editor, CLI о них не знает и `db push`
     попытается выполнить их повторно (ошибка «already exists»). В таком случае продолжайте через SQL Editor.
4. **Адреса для писем.** Authentication → URL Configuration:
   - Site URL — адрес, где открыт сайт (локально, например, `http://localhost:5173`);
   - Redirect URLs — добавьте адреса dev-сервера с `/**`, например
     `http://localhost:5173/**` и `http://127.0.0.1:5173/**` (и порт, который реально выдал Vite).
   Ссылки из писем ведут на `/` (подтверждение email) и `/reset-password` (смена пароля).
5. **Email-авторизация.** Authentication → Sign In / Providers → Email: включите **Confirm email**.
   Рекомендуется задать минимальную длину пароля 8 символов (форма требует столько же).
   Встроенная почта Supabase имеет жёсткие лимиты отправки — для реальной работы подключите собственный SMTP.
6. Перезапустите `npm run dev`.

## Деплой на Vercel

Конфигурация — в `vercel.json`: сборка Vite (`npm ci`, `npm run build`, папка `dist`), переход на `index.html`
для маршрутов React Router при прямом открытии и обновлении страницы (файлы сборки отдаются как есть),
долгий кэш для `/assets/*` и базовые заголовки безопасности. Версия Node — `engines` в `package.json` (24.x).

1. Vercel → Add New → Project → импорт репозитория `digex-campus` (настройки сборки подтянутся из `vercel.json`).
2. **Environment Variables** (Production и Preview):
   - `VITE_SUPABASE_URL` — Project URL проекта digex-campus;
   - `VITE_SUPABASE_PUBLISHABLE_KEY` — **только** publishable-ключ (`sb_publishable_…`);
   - `VITE_DEMO_MODE` — `false` (в production-сборке демо-режим выключен в коде при любом значении).

   Secret key / service_role в Vercel не добавлять: всё с префиксом `VITE_` попадает в браузер,
   а сборка остановится, если найдёт секретный ключ.
3. **Supabase → Authentication → URL Configuration** (после того как известен адрес сайта):
   - **Site URL** — основной адрес сайта, например `https://digex-campus.vercel.app`;
   - **Redirect URLs** — `https://digex-campus.vercel.app/**` (подтверждение почты ведёт на `/`,
     восстановление пароля — на `/reset-password`); адреса локальной разработки оставить.

   Письма ведут на адрес, с которого отправлен запрос (`window.location.origin`). Если адреса нет в списке,
   Supabase подставит Site URL.

## Назначение администратора

Первый зарегистрированный пользователь администратором **не становится** — все новые аккаунты получают роль `student`.

1. Зарегистрируйтесь на сайте и подтвердите email.
2. Откройте `supabase/manual/grant_admin.sql`, замените `ВАШ_EMAIL@example.com` на свой email.
3. Выполните скрипт в Dashboard → SQL Editor. Он должен вернуть ровно одну строку с `role = admin`.
4. Обновите страницу сайта — в боковой панели появится «Панель администратора».

## Обучение, оплата и доступ

Claude и ChatGPT — **разделы одного курса**. Ученики по разделам не распределяются.

- **Разделы и уроки** (Админка → «Разделы и уроки»): создание, правка, порядок (↑/↓), публикация, архив.
  Ничего не удаляется. Архив раздела скрывает только его уроки; общий доступ к курсу не меняется.
- **Оплата** (Админка → «Ученики» → «Управлять»): администратор указывает сумму в сомах и подтверждает оплату.
  Одна оплата открывает **все разделы** на общий период ровно 14 суток (336 часов) с момента активации — по времени
  сервера. Подтверждение атомарно (`admin_confirm_payment`): повтор того же запроса (двойное нажатие, повтор после
  сбоя сети) не создаёт дубль и не сдвигает даты. Пока период действует, новую оплату подтвердить нельзя (продления нет).
- **Отзыв** (`admin_revoke_access`) закрывает все разделы; история не удаляется.
- **Окончание срока** не требует cron: RLS сравнивает даты с серверным `now()` при каждом запросе,
  а открытая страница перепроверяет статус в момент окончания, при возврате во вкладку и раз в 5 минут.
- **До оплаты** ученик видит оба раздела (названия, описания, число уроков), но не содержание уроков.
- **Тесты** (этап 3Б): у урока может быть один тест — вопросы с 4 непустыми вариантами и одним правильным,
  1 балл за верный ответ. Администратор редактирует тест в «Разделы и уроки» → «Тест»; пустой тест опубликовать нельзя.
  Вопросы меняются только функциями `admin_add_question`, `admin_update_question`, `admin_delete_question`,
  `admin_move_question`: они блокируют сначала тест, затем его вопросы по `id` — без взаимных блокировок.
  Ученик получает тест функцией `get_quiz()` — **без правильных ответов** и только при действующем доступе;
  таблицы вопросов доступны только администратору. Баллы считает `submit_quiz_attempt()` в базе: проверяет доступ
  по времени сервера, публикацию, принадлежность вопросов тесту, полноту ответов и версию теста (если тест изменился —
  ученику предлагается загрузить его заново). Повтор одного запроса не создаёт вторую попытку.
  Попытка хранит снимок вопросов и ответов: правка или снятие теста не меняет старые результаты.
- **Результаты и показатели** из базы (`my_quiz_stats`): «Пройдено тестов» — уникальные тесты с попыткой;
  «Попыток» — все отправленные; средний результат — по последней попытке каждого теста; прогресс — пройденные
  из опубликованных тестов программы. История попыток доступна и после окончания доступа.
  В админке «Результаты» — таблица с фильтрами по ученику, разделу и уроку (`admin_quiz_results`).
- Удаление пользователя, у которого есть история оплат, база блокирует: история не должна исчезать.
- Старые таблицы этапа 3А `enrollments` и `payments` (доступ по разделам) оставлены в базе как архив;
  клиентского доступа к ним нет, функции назначения и оплаты по разделам удалены, запись в них запрещена
  триггерами (даже владельцу). Поэтому удалить пользователя, связанного со старыми назначениями, база тоже не даст.

### Известные ограничения

- **Взаимные блокировки при перестановке уроков (не исправлено, принято).** Возможны в двух редких случаях:
  две одновременные перестановки уроков одного раздела, пока в этот раздел добавляют урок;
  обновление нескольких уроков одним прямым запросом к API (интерфейс так не делает).
  PostgreSQL прерывает одну из операций с ошибкой `40P01`: данные не портятся, администратор видит ошибку
  и повторяет действие. Полное исправление — перевод правки уроков на функции базы (затрагивает этап 3А).
- Конкурентные сценарии проверены анализом кода и ревью; автотесты выполняются в PGlite с одним соединением.

## Безопасность данных

- `public.profiles` (id, full_name, role, created_at) создаётся триггером при регистрации, роль всегда `student`.
- Уроки ученик получает только при действующем общем доступе к курсу (`has_course_access()`): опубликованные,
  не архивные, раздел не в архиве, период не отозван, `начало <= now() < окончание`. Иначе — пустой ответ.
  Черновики видит только администратор. Названия и описания разделов доступны любому вошедшему пользователю.
- Оплаты (`course_payments`) ученик только читает (свои). Записывают их лишь функции администратора
  (`SECURITY DEFINER`, `search_path = ''`, явная проверка `is_admin()`, EXECUTE только для `authenticated`).
- Таблицам выданы явные GRANT (настройка «Automatically expose new tables» может быть выключена), RLS включён явно.
- RLS: пользователь читает только свой профиль; администратор читает все.
- Через API можно изменить **только** `full_name` своего профиля (права на уровне колонок).
  Смену роли дополнительно блокирует триггер. Роль выдаётся только SQL-командой владельца БД.
- Проверки в интерфейсе (защищённые маршруты, админка) — удобство; защита данных — в базе.

## Структура

```
src/
  auth/         Supabase Auth: провайдер, ошибки, защита маршрутов
  cabinet/      данные кабинета (настоящий пользователь или демо)
  config.ts     режим работы (демо — только dev)
  data/         содержание курса: course.ts, lessons.ts (Claude и ChatGPT по 6 уроков)
  demo/         ТОЛЬКО режим разработки: вымышленные ученики и переключатель
  lib/          supabase-клиент, доступ (14 дней), форматирование, валидация
  components/ layouts/ pages/ styles/
supabase/
  migrations/   SQL-миграции (по порядку имени)
  seed/         начальное наполнение (генерируется: node scripts/generate-seed.mjs и generate-quiz-seed.mjs)
  manual/       ручные SQL-команды (назначение администратора, проверка старых оплат)
src/api/        запросы к базе: learning.ts (ученик), admin.ts (администратор)
```

## Программа уроков в сборке

`src/data/lessons.ts` — исходник начального наполнения и данные демо-режима. В обычную сборку он **не попадает**:
ученик получает уроки только из базы после проверки доступа. Изменили программу в файле — перегенерируйте
`supabase/seed/initial_content.sql` командой `node scripts/generate-seed.mjs` (на уже наполненную базу это не влияет).

## Тесты в демо-режиме

В демо-режиме разработки тест проверяется в браузере на локальных данных и явно подписан как демонстрационный;
в обычной сборке вопросов и ответов нет.
